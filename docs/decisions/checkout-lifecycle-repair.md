# Checkout lifecycle repair

Root cause: checkout deducts inventory before saving the header, items and tender changes. Cancellation updates status and restores inventory in separate requests; retries can increase stock twice. Missing shipping columns encourage lossy fallback orders.

Buyer journey: validate the complete request, then save the order, all lines, inventory deductions, discount use and gift-card debit in one server-only transaction. Failure leaves none of those changes. Existing receipt and payment initiation follow the committed order. No result claims payment or a provider refund without provider evidence.

Merchant journey: cancellation locks the order and restores only recorded deductions once, including variants and gift-card balance. Paid, fulfilled and archived orders require the separate refund/return process. Legacy orders have unknown deduction provenance; cancellation must stop for inventory reconciliation rather than guess. Cancelled orders cannot be reopened through fulfillment.

Engineering: service-only RPCs, pinned search paths, explicit project scope, stable product/variant lock order, item-level deduction quantities, order-level tender lineage. Recover shipping fields from canonical migration 069; widen header quantity for 24 lines while each line remains 1–20. Discount limits and gift balances are checked again under locks. Keep payment status unchanged during cancellation so provider callbacks can reject cancelled orders.

Completion: actual SQL transaction tests for success, header/item failure rollback, insufficient later stock, duplicate demand, variants, stale discounts/gifts, cancellation replay and role denials; application wiring, full CI, QA-only migration and rollback probes. Browser authenticated journeys, real providers and timing remain distinct gates until actually verified.

Tender/return repair: a full gift-card debit settles the order only when the known cash remainder is zero. Record its paid ledger entry in the same transaction. Mixed tender becomes paid only after cash verification. A full refund restores recorded gift credit once; a cash receipt remains mandatory for positive cash amounts. Merchants separately confirm every item was received in resalable condition before restocking all recorded deductions once. Missing inventory or legacy provenance blocks the whole return. Returned orders are archived and cannot be fulfilled again. Preserve disabled/expired gift-card restrictions and discount usage for completed sales. Partial returns and automated provider refunds are not implied by these full-order actions.

Retry repair: buyers keep a UUID attempt across network failures and refreshes, rotate it after confirmed success or changed input, and carry it into offline sync. A server-generated fingerprint binds the parsed input to that attempt. A private project/attempt receipt serializes concurrent saves before validating mutable stock or tender, returns the original order on replay, and refuses changed input. Lookup runs before mutable catalog/tender validation. Replays never repeat provider initiation, notifications or delivery. A interrupted follow-up may return a saved order without a payment link; it must tell the buyer to contact the shop, never silently create another order. Receipt evidence prevents deleting just its order. Existing clients without an attempt remain compatible and lack deduplication until upgraded.

Verification checkpoint: 32 actual SQL transaction tests, PayPal binding checks, retry/offline regressions and hosted rollback assertions pass. Actual Next.js components pass phone retry/refresh and desktop fulfilled-order refund/return checks with explicit network fixtures; the real API rejects unauthenticated merchant requests. Scoped return-receipt state disables repeated restocking. Payment/provider binding is mandatory and rechecked under the order lock.
